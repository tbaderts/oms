# Design — SPEC-0005: Fix contract paths and merge into Contracts view

## Context

All in `developer-cockpit/`:

- `src/shared/types/config.ts` — `SpecsConfig { openApiPaths, avroPaths, autoGenerate }`;
  `DEFAULT_CONFIG.specs` points at `oms-core/src/main/{openapi,avro}` (gone since the contracts
  moved to `oms-contracts/`).
- `src/main/services/ConfigService.ts` — `CONFIG_DIR = ~/.developer-cockpit` (module constant);
  `load()` merges saved `config.json` over the defaults one level deep (`merge()`), `save()` writes
  it. Not unit-tested today.
- `src/main/services/SpecsService.ts` — `discoverFiles()` scans the configured dirs (non-recursive),
  `readFile` (workspace check), `writeFile` (`validatePathWithinSpecDirs`, a bare
  `resolved.startsWith(absDir)`: a sibling such as `…/openapi-old/x.yml` passes), `validate`,
  `parseEntities()` (OpenAPI `components.schemas` + Avro records/enums).
- `src/main/ipc/specs.ipc.ts` — module-level singletons `specsService`/`codeGenService`, created on
  first call with the config of that moment, so later Settings changes are ignored until restart.
- `src/main/services/CodeGenService.ts` — three tasks mapped to `gradlew(.bat) -p oms-core
  openApiGenerateCmd|openApiGenerateQuery|openApiGenerateAvro`, run with `execFile` from the
  workspace root. `openApiGenerateAvro` no longer exists (`oms-core/build.gradle` comment), models
  are generated by `oms-contracts` (`openApiGenerateCmdModels`, `openApiGenerateQueryModels`, Avro
  plugin `com.github.davidmc24.gradle.plugin.avro` → `generateAvroJava`), and on Windows Node's
  `execFile` refuses `.bat`/`.cmd` without a shell (EINVAL since the CVE-2024-27980 fix).
- Renderer: `stores/navigation.ts` (`ViewId`, `NAV_ITEMS`, used by `Sidebar` and `CommandPalette`),
  `components/layout/ContentArea.tsx` (`VIEW_MAP`, lazy views), views `specs-editor/`,
  `domain-model/`, `code-generator/` all backed by `stores/specs.ts`; `dashboard/DashboardView.tsx`
  quick link to `specs-editor`.
- Closest examples: the tabbed `views/requirements/RequirementsView.tsx` (Tabs over existing tab
  components) for the merged view; `SpecCli` (injectable runner, explicit argv, no user input in
  commands) for the code generation runner; `test/main/*` and `test/renderer/*` (Vitest, jsdom,
  Testing Library) for tests.
- Read: CLAUDE.md (Code Generation), `oms-contracts/build.gradle`, `oms-core/build.gradle`,
  `developer-cockpit/spec/02-information-architecture.md`, `03-features.md`, `04-backend-services.md`,
  `05-data-model.md`. OMS framework specs do not apply (no OMS module changes).

## Approach

### 1. Paths and migration (AC-1, AC-2)

- `config.ts`: `DEFAULT_CONFIG.specs = { openApiPaths: ['oms-contracts/src/main/openapi'], avroPaths:
  ['oms-contracts/src/main/avro'], autoGenerate: false }`, plus
  `export const LEGACY_SPECS_PATHS = { openApiPaths: ['oms-core/src/main/openapi'], avroPaths: ['oms-core/src/main/avro'] }`.
- `ConfigService` gets `constructor(private configDir = path.join(os.homedir(), '.developer-cockpit'))`
  (file = `<configDir>/config.json`) so tests use a temp dir; existing `new ConfigService()` calls
  are unchanged.
- New exported pure function `migrateConfig(config): { config, migrated: boolean }` in
  `ConfigService.ts`: for each of `openApiPaths`/`avroPaths`, if the saved array deep-equals the legacy
  array, replace it with the default. `load()` calls it after `merge()` and, if `migrated`, saves the
  file once and logs `[config] migrated legacy contract paths to oms-contracts`.

### 2. Live paths (AC-3)

`specs.ipc.ts`: replace the singletons by getters that rebuild when the config object changes
(`ConfigService.save()` replaces `this.config` with the saved object, so identity is a reliable
signal):

```ts
let cached: { config: CockpitConfig; specs: SpecsService; codeGen: CodeGenService } | null = null;
function services(configService: ConfigService) {
  const config = configService.getConfig();
  if (!cached || cached.config !== config) {
    cached = { config, specs: new SpecsService(config.general.workspaceRoot, config.specs),
               codeGen: new CodeGenService(config.general.workspaceRoot) };
  }
  return cached;
}
```

`registerSpecsIpc` is exported unchanged in signature; tests drive it with a fake `ipcMain`
(`handle(channel, fn)` into a map) and a real `ConfigService` on a temp dir.

### 3. Domain Model (AC-4)

No parser change: with the paths fixed, `parseEntities()` reads `oms-contracts`. Verified by a test
against the repository's own `oms-contracts` (read-only).

### 4. Code generation (AC-5)

`CodeGenTask` (shared/types/specs.ts) gains `module: string` and `gradleTasks: string[]`
(`inputSpec`/`outputPackage` kept for the card):

| id | name | module | gradleTasks | inputSpec → outputPackage |
|---|---|---|---|---|
| `contracts` | Contract models | `oms-contracts` | `generateAvroJava`, `openApiGenerateCmdModels`, `openApiGenerateQueryModels` | `openapi/*.yml, avro/*.avsc` → `org.example.common.model.{cmd,query,msg}` |
| `api` | API interfaces | `oms-core` | `openApiGenerateCmd`, `openApiGenerateQuery` | `oms-cmd-api.yml, oms-query-api.yml` → `org.example.common.api (ExecuteApi, SearchApi)` |

`CodeGenService(workspaceRoot, runner = execFileRunner, platform = process.platform)`:
- unknown id → `{ success: false, output: 'Unknown task: …' }` without calling the runner;
- `cwd = <root>/<module>`; POSIX: `runner('./gradlew', gradleTasks, { cwd })`; Windows:
  `runner(process.env.ComSpec ?? 'cmd.exe', ['/d', '/s', '/c', 'gradlew.bat', ...gradleTasks], { cwd })`.
  Every argument is a constant from the task table — nothing from the renderer reaches the shell
  (the renderer only sends a task id, which must match the table);
- timeout 10 min, maxBuffer 10 MB; non-zero exit → `success: false` with stdout+stderr; logs
  `[codegen] <id> <exit> <ms>`.

Task order in the table is the *Run all* order (`stores/specs.ts` `runAllCodeGen` already iterates
`codeGenTasks` in order), so contract models run before API interfaces.

### 5. Contracts view (AC-6)

- `navigation.ts`: `ViewId` drops `specs-editor`, `domain-model`, `code-generator`, adds `contracts`;
  `NAV_ITEMS` gets `{ id: 'contracts', label: 'Contracts', group: 'Development', icon: 'FileCode' }`
  where Specs Editor was.
- New `views/contracts/ContractsView.tsx`: full-height column with `Tabs` (`editor` / `domain-model`
  / `code-generation`, labels *Editor*, *Domain Model*, *Code Generation*) rendering the existing
  `SpecsEditorView`, `DomainModelView`, `CodeGeneratorView` unchanged. Tab content is mounted only
  when active (Radix default), so each view loads its data on first open as today.
- `ContentArea.tsx`: `contracts: ContractsView` (lazy) replaces the three entries.
- `DashboardView.tsx`: quick link `{ id: 'contracts', label: 'Contracts', description: 'Edit
  OpenAPI & Avro, browse the domain model, run code generation' }`.
- Sidebar/CommandPalette need no change (they render `NAV_ITEMS`).

### 6. Save guard (AC-7)

`validatePathWithinSpecDirs` / `validatePathWithinWorkspace`: allowed if `resolved === absDir` or
`resolved.startsWith(absDir + path.sep)` (prefix-sibling fix), and the extension is `.yml`, `.yaml`
or `.avsc`.

Mapping of What Changes: defaults/migration → §1; live paths → §2; tasks → §4; Contracts view and
links → §5; (Domain Model works again → §1/§3; save guard → §6).

## Contract Changes

None — the cockpit reads and edits the existing files in `oms-contracts/src/main/`; no schema change.

## Data & Persistence

None in OMS. The cockpit's `~/.developer-cockpit/config.json` gets a one-time migration that only
replaces the two exact legacy arrays (§1); all other keys and custom values are written back
unchanged. Rollback: an older cockpit would read the new paths, which are valid.

## Events & Messaging

None — no order events, outbox or Kafka. No new cockpit event.

## Domain, State & Orchestration

None — no OMS state. Input validation in main: task ids must match the table; save paths must lie
inside the configured contract dirs (§6).

## Alternatives & Decisions

- **Merge into one Contracts view instead of deleting the Specs Editor** (agreed with the requester):
  contract-first support stays; three sidebar entries become one.
- **Reuse the three existing views as tabs** rather than redesigning them: smallest change; their
  stores and tests stay valid.
- **Migrate only exact legacy values**: never overrides a deliberate user choice. Rejected:
  "replace any path that doesn't exist" (would silently rewrite a typo the user is fixing, or a path
  on a not-yet-mounted drive).
- **Rebuild services on config identity change** instead of an explicit `config:changed` event:
  no new plumbing; `save()` already swaps the object.
- **Windows: `cmd.exe /d /s /c gradlew.bat …` with constant args** instead of `execFile(…, { shell:
  true })` with a joined string: explicit argv, no user input involved. Rejected: running Gradle via
  the root composite wrapper (`-p <module>`): each module is an independent build (CLAUDE.md) with its
  own wrapper.
- **Two code generation tasks** (models, interfaces) matching CLAUDE.md's two regeneration commands.
- **Changed during implementation (runtime check, T-7): `.\gradlew.bat`, not `gradlew.bat`.** With
  `NoDefaultCurrentDirectoryInExePath` set (a Windows hardening option; set in this environment),
  `cmd.exe` does not look in the working directory for a bare command name, so `gradlew.bat` was
  "not recognized" (exit 1). An explicit relative path is always resolved against `cwd`, and it
  contains no spaces whatever the workspace path is, so no quoting is needed.
- **No new dependency or build change.**

## Risks & Mitigations

- *Gradle runs are slow / need a JDK*: unchanged risk; 10 min timeout, output shown; verified once at
  runtime in verify.
- *Old view ids persisted somewhere*: navigation state is not persisted (zustand without persist),
  and `ViewId` is a TS union, so the typecheck finds every stale reference.
- *Migration rewrites a user's file*: only the two exact legacy arrays; covered by AC-2 tests,
  including "custom paths kept".
- *Shell injection on Windows*: only constant table values reach `cmd.exe`; unknown ids never start a
  process (AC-5 test).
