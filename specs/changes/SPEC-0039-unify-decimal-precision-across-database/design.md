# Design — SPEC-0039: Unify decimal precision across database, Avro and OpenAPI

## Context

**Avro** (`oms-contracts/src/main/avro`):
- `Order.avsc` (the command payload inside `OrderCreateCmd`): `orderQty`, `cashOrderQty`,
  `strikePrice`, `price`, `stopPx` are `double`.
- `Quote.price` and `QuoteRequest.quantity` are `double`.
- `OrderMessage`: `cashOrderQty`, `orderQty`, `price`, `stopPx`, `strikePrice` are `decimal(18,2)`;
  `cumQty`, `leavesQty` are `decimal(18,4)`.
- `Execution` (`lastQty`, `lastPx`, `cumQty`, `leavesQty`, `avgPx`) and `OrderExecution` (those
  plus `price`, `orderQty`) are `decimal(18,4)`.
- Compatibility guards: `OrderMessageCompatibilityTest`, `CommandMessageCompatibilityTest`,
  `ExecutionCompatibilityTest`, `OrderExecutionCompatibilityTest` against `compat/*-baseline.json`.

**OpenAPI** (`oms-cmd-api.yml` v2.0.0, `oms-query-api.yml` v1.0.0): `type: number`, no bound.
- Command `Order`: `orderQty`, `cashOrderQty`, `strikePrice`, `price`, `stopPx`.
- Command `Execution`: `lastQty`, `lastPx`, `cumQty`, `leavesQty`.
- Query `OrderDto`: `orderQty`, `cashOrderQty`, `placeQty`, `cumQty`, `leavesQty`, `allocQty`,
  `strikePrice`, `price`, `stopPx`.
- Query `ExecutionViewDto`: `price`, `orderQty`, `lastQty`, `lastPx`, `cumQty`, `leavesQty`,
  `avgPx`.

The models are generated by the `spring` generator in oms-contracts with bean validation (fields
are `BigDecimal`, nested objects `@Valid`); oms-core validates request bodies and answers the
`validation-failed` 400 (`GlobalExceptionHandler`, SPEC-0034).

**Database:** unconstrained `NUMERIC` everywhere.
- `orders`: `order_qty`, `cash_order_qty`, `place_qty`, `cum_qty`, `leaves_qty`, `alloc_qty`,
  `strike_price`, `price`, `stop_px`.
- `executions`: `avg_px`, `cum_qty`, `last_px`, `last_qty`, `leaves_qty`, `day_order_qty`,
  `day_cum_qty`, `day_avg_px`.
- `order_execution_view`: `price`, `order_qty`, `last_qty`, `last_px`, `cum_qty`, `leaves_qty`,
  `avg_px`.

Latest changelog: `007-projections.yaml` (changesets 016, 017).

**Code that rounds:**
- `CalculateOrderQuantitiesTask` sets `cumQty` and `leavesQty` with
  `setScale(QUANTITY_SCALE = 4, HALF_UP)`. An 8-decimal fill would be rounded silently.
- Exchange simulator: `CommandGateway` rounds outgoing fill values with
  `setScale(DECIMAL_SCALE = 4, HALF_UP)`; `FillSlicer.QUANTITY_SCALE = 4`; `ExchangeEngine` rescales
  `orderQty` to it.

**Kafka commands** reach oms-core as Avro records and are turned into command models with
`objectMapper.convertValue(msgCmd, OrderCreateCmd.class)` (`CommandListener`); with `double` fields
that passes through binary floating point.

**Closest examples:** `CommandIdBackfillMigrationIntegrationTest` (migrate to a tag, insert legacy
rows, migrate the rest) for the migration tests; `OrderExecutionSchemaTest` for a schema-walking
contract test; `CommandControllerWebMvcTest` (SPEC-0034) for validation-failed tests;
`AbstractFillFlowIntegrationTest` (SPEC-0020) for end-to-end fills.

**Read:** `oms-framework/openapi-contracts.md`, `error-handling.md`, `validation-rules.md`,
`interfaces/avro-messages.md`, the policies.

## Approach

One rule, `decimal(18,8)`, stated in each layer's own terms:

| Layer | Expression |
|---|---|
| Avro | `{"type":"bytes","logicalType":"decimal","precision":18,"scale":8}` in a nullable union |
| OpenAPI | `type: number` + `x-field-extra-annotation: "@jakarta.validation.constraints.Digits(integer = 10, fraction = 8)"` + a description sentence stating the bound |
| Database | `NUMERIC(18,8)` |
| Java (oms-core, simulator) | scale 8, never rounded on the way through |

- **Kafka boundary:** Avro's decimal conversion refuses a value with more than 8 decimals or more
  than 18 digits when it is serialised, so a producer cannot send one. Values with fewer decimals
  are rescaled losslessly.
- **REST boundary:** the generated models carry `@Digits(integer = 10, fraction = 8)` on every
  price and quantity field; the existing `@Valid` request handling turns a violation into the
  `validation-failed` 400 naming the field path (e.g. `order.price`, `execution.lastPx`).
- **Internal arithmetic:** `CalculateOrderQuantitiesTask.QUANTITY_SCALE` becomes 8, and its rounding
  mode becomes `UNNECESSARY`, since sums and differences of scale-8 inputs never need rounding. Any
  violation fails loudly instead of rounding. The simulator's `DECIMAL_SCALE` and `QUANTITY_SCALE`
  become 8. The simulator keeps `HALF_UP` for prices it generates itself.
- **Mappers:** unchanged in logic. `OrderMessageMapper`, `ExecutionMessageMapper`,
  `OrderExecutionMessageMapper` pass `BigDecimal` through. `CommandListener.convertValue` now
  converts `BigDecimal` to `BigDecimal`, exactly. The streaming service's `toBigDecimal` already
  accepts `BigDecimal`.

## Contract Changes

**Avro, all BREAKING** (P-04: declared in the proposal and versioned by new baselines):

- `Order.avsc`: `orderQty`, `cashOrderQty`, `strikePrice`, `price`, `stopPx` →
  `["null", {"type":"bytes","logicalType":"decimal","precision":18,"scale":8}]`, `"default": null`.
- `Quote.avsc` `price`, `QuoteRequest.avsc` `quantity`: same.
- `OrderMessage.avsc`: `cashOrderQty`, `orderQty`, `price`, `stopPx`, `strikePrice` (scale 2 → 8);
  `cumQty`, `leavesQty` (scale 4 → 8).
- `Execution.avsc` (5 fields) and `OrderExecution.avsc` (7 fields): scale 4 → 8.
- Docs on each field state the precision.
- `compat/*-baseline.json` for `OrderMessage`, `CommandMessage`, `Execution`, `OrderExecution` are
  regenerated from the new schemas: they mark the new major version, and the compatibility tests
  then guard it from here on. The test Javadocs name SPEC-0039 as the release the baseline belongs
  to. `SchemaCompatibility` does not compare logical types, so the scale change itself would not
  have failed those tests; the new `DecimalPrecisionContractTest` is what pins it.

**OpenAPI:**

- `oms-cmd-api.yml`: `info.version` `3.0.0`. The 9 command fields gain the extension and the
  sentence "At most 10 integer digits and 8 decimal places."
- `oms-query-api.yml`: `info.version` `2.0.0` (response values can now carry 8 decimals). The 16
  query fields gain the same extension and sentence.

Generated: `cmd.Order`, `cmd.Execution`, `query.OrderDto`, `query.ExecutionViewDto` fields annotated
`@Digits(integer = 10, fraction = 8)`; `msg.*` decimal fields as `BigDecimal` with the new scale.

## Data & Persistence

New `oms-core/src/main/resources/db/changelog/008-decimal-precision.yaml`, included last:

- changeset `018-tag-before-decimal-precision`: `tagDatabase: before-008-decimal-precision` (for
  the migration test, as `014` did for SPEC-0018).
- changeset `019-decimal-precision`, one transaction (Postgres DDL is transactional):
  1. a `sql` `DO $$ … $$` block that loops over the 24 `(table, column)` pairs and, for each, runs
     `SELECT count(*) FROM <table> WHERE scale(<col>) > 8 OR abs(<col>) >= 1e10`; on any hit it
     `RAISE EXCEPTION 'decimal precision check failed: %.% has % value(s) beyond NUMERIC(18,8)'`,
     which aborts the changeset before any type changes (AC-3);
  2. `modifyDataType` to `NUMERIC(18,8)` for each of the 24 columns.
  Rollback: `modifyDataType` back to `NUMERIC` (lossless).

No backfill: the check guarantees the cast changes no value (AC-2). JPA entities are unchanged:
`ddl-auto: validate` accepts `BigDecimal` for `NUMERIC(18,8)`.

## Events & Messaging

- `order_events` (P-05): unchanged; snapshots are JSON numbers and keep whatever the entity holds
  (at most 8 decimals now).
- Outbox (P-06): unchanged in mechanism; payloads now carry scale-8 decimals. `PROJECTION` rows
  staged before deployment hold the old `OrderExecution` encoding and must be published before it
  (the runbook drains the outbox; documented constraint from SPEC-0020).
- Topics `commands`, `oms_orders`, `oms_executions`, `oms_order_executions`: same names, new schema
  versions. **Deployment runbook** (KB): stop producers (simulator, clients); wait until the outbox
  is empty and consumers have caught up; set each subject's compatibility to `NONE`
  (`PUT /config/<subject>`); deploy oms-core, oms-streaming-service and oms-exchange-simulator
  together; set compatibility back to `BACKWARD`. Confirmed at proposal approval.
- Idempotency (P-08): unchanged.

## Domain, State & Orchestration

- No state machine change.
- `CalculateOrderQuantitiesTask`: scale 8, `RoundingMode.UNNECESSARY` (see Approach).
- Validation: REST precision violations are bean-validation failures → `validation-failed` 400
  (P-13). Kafka values cannot exceed the schema. No new validation task.

## Alternatives & Decisions

- **`decimal(18,8)` everywhere, prices and quantities alike.** Requester's decision (2026-11-01).
- **OpenAPI bound via `@Digits` on the generated models.** Rejected:
  - `multipleOf: 0.00000001`: openapi-generator emits no bean validation for it, and float
    `multipleOf` checks in other tools (e.g. the cockpit's checker) give false failures.
  - `maximum`/`minimum` alone: bounds the magnitude, not the decimals.
  - A hand-written validation task: duplicates the contract (P-02).
- **Migration refuses instead of rounding** (proposal). Rejected: `USING round(col, 8)` (silently
  changes money values).
- **`RoundingMode.UNNECESSARY` in `CalculateOrderQuantitiesTask`.** Rejected: keeping `HALF_UP`
  (would hide a precision bug as a rounding).
- **Same topics, drained deployment** (confirmed at approval). Rejected: `*_v2` topics (every
  configuration changes; no unknown consumers exist).
- **New baselines rather than keeping the old ones**: the old baselines describe a version that is
  intentionally incompatible; keeping them would make every build fail, and their purpose (guard
  the released version) moves to the new one.
- **Changed during implementation (T-6): Kafka order creation is mapped explicitly** with
  `OrderMapper.toCmdOrder(msg.Order)` (MapStruct; ISO-string `sendingTime`/`expireTime` parsed to
  `OffsetDateTime`) instead of `objectMapper.convertValue`. AC-6's test found that `convertValue`
  on an Avro record always fails (Jackson walks `getSchema()`), so creating an order over Kafka had
  never worked; `CommandListenerTest` mocked the `ObjectMapper` and could not see it. Fills over
  Kafka were already mapped this way (`toCmdExecution`). The listener no longer needs an
  `ObjectMapper`.
- No new dependency or build change (P-17): `x-field-extra-annotation` is a built-in generator
  extension; `jakarta.validation` is already on the classpath.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| An old producer or consumer meets a new message | One coordinated deployment after draining; runbook in the KB |
| Schema Registry rejects the double→decimal registration | Compatibility set to `NONE` for the deployment, then back |
| Existing data beyond the precision | Migration refuses, naming the column (AC-3); none expected |
| Values with trailing zeros beyond 8 places (e.g. `1.000000000`) are refused | `@Digits` counts the scale as sent; documented in the contract description ("at most 8 decimal places, as written") |
| Some test relies on 2- or 4-decimal rounding | Full suites of every affected module run in verify |
