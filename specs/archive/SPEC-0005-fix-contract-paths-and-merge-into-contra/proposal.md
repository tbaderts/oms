# Proposal — SPEC-0005: Fix contract paths and merge into Contracts view

> **Stage 1 of 3 — why and what, not how.** The acceptance criteria below are the contract that
> the verify stage checks. If they are vague, the goal cannot be proven met.

## Why

Three developer-cockpit views work on the OMS contracts (OpenAPI and Avro): **Specs Editor**,
**Domain Model** and **Code Generator**. All three are broken today:

- `DEFAULT_CONFIG.specs` (`developer-cockpit/src/shared/types/config.ts`) and every saved
  `~/.developer-cockpit/config.json` point at `oms-core/src/main/openapi` and `oms-core/src/main/avro`.
  Those folders were removed when the contracts moved to `oms-contracts/` (CLAUDE.md: *"All contracts
  live in `oms-contracts/` and nowhere else"*). `SpecsService.discoverFiles()` therefore finds nothing:
  the Specs Editor shows an empty file list and Domain Model shows no entities. The requester ran into
  this ("I don't see anything showing up in … spec editor").
- `specs.ipc.ts` creates `SpecsService` once with the config of its first call, so correcting the
  paths in Settings has no effect until the app restarts.
- `CodeGenService` runs `gradlew.bat -p oms-core openApiGenerateCmd|openApiGenerateQuery|openApiGenerateAvro`.
  The models are generated by `oms-contracts` now (`openApiGenerateCmdModels`,
  `openApiGenerateQueryModels`, Avro plugin `generateAvroJava`); `oms-core` generates only the API
  interfaces, and `openApiGenerateAvro` no longer exists. On Windows, Node also refuses to `execFile`
  a `.bat` without a shell, so no task can start at all.

On top of that, these three views take three sidebar entries for one concern, while the requester
finds the cockpit cluttered.

Requester goal (ticket.md): *"The spec editor tab is stale and shows nothing … Agreed direction:
fix the paths (defaults and existing saved config) so these views work again, and merge Specs
Editor, Domain Model and Code Generator into one Contracts view with tabs to reduce sidebar
clutter."*

If we do nothing, three views stay dead weight in the sidebar and contract-first work (P-02) has no
support in the cockpit.

## What Changes

- Default contract paths become `oms-contracts/src/main/openapi` and `oms-contracts/src/main/avro`.
- A saved config whose contract paths are exactly the old `oms-core` defaults is migrated to the new
  defaults when it is loaded, and saved back. Custom paths a user set are left alone.
- Changed contract paths in Settings take effect without restarting the cockpit.
- Code generation tasks match the current build:
  - **Contract models** — `oms-contracts`: `generateAvroJava openApiGenerateCmdModels openApiGenerateQueryModels`;
  - **API interfaces** — `oms-core`: `openApiGenerateCmd openApiGenerateQuery`.
  Each runs the module's own Gradle wrapper in that module's folder, and works on Windows.
  *Run all* runs contract models first.
- One **Contracts** sidebar entry (group *Development*) replaces Specs Editor, Domain Model and Code
  Generator. The view has three tabs, **Editor**, **Domain Model** and **Code Generation**, which
  show the existing content of the three views. The command palette and the Dashboard link go to it.
- No change to any OMS module, contract, database or topic. Nothing is **BREAKING** outside the
  cockpit; inside it, the three old view ids are removed.

## Scope

### In scope

- Default paths, migration of saved configs with the legacy defaults, live reload of contract paths.
- Correct code generation tasks and their invocation on Windows and POSIX.
- The merged Contracts view and the navigation changes (sidebar, command palette, Dashboard link).
- Tests for every AC; a runtime check in the built app that the editor lists the contract files.
- Updating `developer-cockpit/spec/` pages that describe these views (features, backend services,
  data model/config, information architecture, storyboard cross-links).

### Out of scope

- The Dashboard redesign and Spec Tickets layout (SPEC-0006). This ticket only repoints the existing
  Dashboard quick link.
- New contract-editing features (schema-aware validation, diff against git, references navigation).
- Improving Domain Model parsing (e.g. resolving `$ref`s across `schema.yml`).
- Running a full `./gradlew build` from the cockpit, or streaming Gradle output while it runs.
- Any change to the OMS Gradle builds themselves.

## Acceptance Criteria

- **AC-1** — Given a fresh config (no saved file) and a workspace that contains
  `oms-contracts/src/main/openapi/*.yml` and `oms-contracts/src/main/avro/*.avsc`, when the contract
  files are discovered, then every `.yml`/`.yaml` there is returned as `openapi` and every `.avsc` as
  `avro`, and nothing is read from `oms-core/`.
- **AC-2** — Given a saved config whose `specs.openApiPaths` is `["oms-core/src/main/openapi"]` and
  `specs.avroPaths` is `["oms-core/src/main/avro"]`, when the cockpit loads its config, then both are
  replaced by the `oms-contracts` defaults, the file on disk is rewritten with them, and every other
  setting is unchanged. Given saved paths that differ from the legacy defaults in any way, then they
  are kept as they are.
- **AC-3** — Given the cockpit has already discovered contract files, when the contract paths are
  changed and saved in Settings, then the next discovery uses the new paths without a restart.
- **AC-4** — Given the repository's `oms-contracts` contracts, when Domain Model loads, then it
  returns entities from both sources, including at least `OrderCreateCmd` (Avro or OpenAPI) and the
  `Side` enum.
- **AC-5** — Given the code generation tasks, when they are listed and run, then there are exactly two
  tasks: *Contract models*, running `generateAvroJava openApiGenerateCmdModels openApiGenerateQueryModels`
  with the `oms-contracts` Gradle wrapper and working directory `oms-contracts/`, and *API interfaces*,
  running `openApiGenerateCmd openApiGenerateQuery` with the `oms-core` wrapper and working directory
  `oms-core/`. On Windows the wrapper is started through the command shell. A non-zero exit returns
  `success: false` with the output, an unknown task id is rejected without starting a process, and
  *Run all* runs contract models before API interfaces.
- **AC-6** — Given the cockpit is open, when the sidebar, command palette and Dashboard links render,
  then there is one **Contracts** entry and no Specs Editor, Domain Model or Code Generator entry, and
  opening Contracts shows the tabs **Editor**, **Domain Model** and **Code Generation**, each showing
  that existing view's content (file list and editor, entity list, task cards).
- **AC-7** — Given a contract file outside the configured contract folders (or outside the
  workspace), when the editor tries to save it, then the write is rejected and the file is unchanged.

## Impact

| Area | Impact |
|---|---|
| Modules | developer-cockpit only (main: ConfigService, SpecsService, CodeGenService, specs IPC; renderer: navigation, ContentArea, new Contracts view, Dashboard link, Settings unchanged). |
| Contracts (OpenAPI / Avro) | none; the cockpit only reads/edits the existing files in `oms-contracts/src/main/` (editing them stays subject to P-01/P-04 like any other edit). |
| Data (tables, migrations) | none in OMS. The cockpit's own `~/.developer-cockpit/config.json` gets a one-time, value-preserving migration of the legacy contract paths. |
| Events / Kafka topics | none |
| Consumers (oms-ui, oms-mcp-server, downstream) | none. Inside the cockpit the view ids `specs-editor`, `domain-model`, `code-generator` are replaced by `contracts`. |
| Knowledge base | `developer-cockpit/spec/` pages for these views (03-features, 04-backend-services, 05-data-model config, 02-information-architecture, 11-storyboards cross-links). No `oms-knowledge-base/` change. |

## Open Questions

- [resolved] Delete the Specs Editor instead of fixing it? → No (requester agreed): contract-first is
  a core principle (P-02) and Domain Model/Code Generation share its service; merge instead of three
  entries.
- [resolved] Which saved paths are migrated? → assumption: only the exact legacy defaults
  (`oms-core/src/main/openapi`, `oms-core/src/main/avro`). Anything a user customised is respected;
  the Settings tab still lets them change it.
- [resolved] Code generation granularity → assumption: two tasks (contract models, API interfaces)
  instead of the old three, matching CLAUDE.md's two regeneration commands; a full `./gradlew build`
  stays in the terminal.
- [resolved] Tab names inside Contracts → assumption: Editor, Domain Model, Code Generation. Cheap to
  rename.
- [deferred] Running code generation for consumer modules (oms-streaming-service, oms-mcp-server) →
  they generate nothing themselves (CLAUDE.md), so there is nothing to run.
